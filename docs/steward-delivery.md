# 目标投递与进度（P4-1）

实现：`api/app/delivery.py` + `goal_deliveries` 表、`GET/POST /api/deliveries`、
管家上下文里的 `delivery` 段（`steward._delivery_block`）、界面 `DeliveryPanel`。
判据：`api/tests/test_delivery.py`（27 例）、`test_delivery_api.py`（15 例）、
`web/src/deliveryView.test.ts`（10 例）。

## 1. 要解决的不是"能不能起树"，而是"起完就断线"

`start_task` 原先起完树就返回一个 `root_id`，之后管家与那棵树再无联系。用户于是只能
自己去翻看板："第几步了？卡在哪？" —— **而这两句话恰是管家唯一该回答的东西。**

## 2. 两条设计规矩

### 2.1 不做后台推送，只在被问到时才算

`delivery.progress()` 是**纯计算**：调用方给树快照与未清债，它给"第几步、卡在哪"。

为什么不做推送：推送会把"树在动"变成消息流，而这个工具已经有看门狗在做后台判断。
管家是**对话者**，它的报告应当发生在**有人看的时候**。另外，直接读最新状态比维护
一份增量推送更不容易出错 —— 不存在漏推，也不存在状态漂移。

管家每次拼上下文时读一次（`steward._delivery_block`），界面打开面板时读一次
（`GET /api/deliveries/latest`）。

### 2.2 "第几步"必须是可核对的

不报"大概跑了一半"，而报 `已完成 12 / 总计 30`，并给出：

| 字段 | 回答 |
|---|---|
| `done` / `total` / `ratio` | 做到哪了 |
| `frontier` | **最深的未完成节点** —— "第几步"最接近的答案 |
| `stuck` | 阻塞/失败节点 —— "卡在哪" |
| `blocking_obligations` | 未清阻断债 —— "卡在哪"的另一半 |
| `next_step` | 一句话：现在该看什么 |

**分母是节点数**，不是"工作量"：没有可靠的工作量单位，硬造一个（比如按 token 折算）
会比"数节点"更假。

## 3. 四条"不编"的规矩

| 规矩 | 为什么 |
|---|---|
| `ratio` 分母为 0 时给 `null`，**不给 0** | 0% 会被读成"一点没做"，而真相可能是读错了树 |
| **取消掉的分支不算完成** | 取消的分支没有被做出来；算进完成率会让"进度 90%"读起来像"快好了"，而真相是"有一部分你决定不做了" |
| **没查债 ≠ 没有债** | `open_obligations=None` 表示"调用方没去查"，会写进 `incomplete`；把"没查"读成"没有"是这一层最容易犯的错 |
| 空树给 `available: false` + 原因 | 报 0/0 看起来像"还没开始"，而真相可能是投递记录指向了一棵已经不存在的树（换工程、删库） |

**卡点优先于进度说话**：有阻断债或卡住节点时，`next_step` 先说那个。
否则用户看到"进度 90%"会以为一切正常，直到很久之后才发现有人在等。

## 4. 投递记录的两条边界

* **`root_id` 必填**。一次"投递"的定义就是"确实起出了一棵树" —— 起树失败时留下
  一条记录，会让"我投过这个目标"看起来像发生过。
* **记账失败不让起树回滚**。树已经起来了，记账只是"报告里少一条"，
  而回滚一棵已经跑起来的树要糟得多。

`author` 是**自报的**名字且**允许为空**：这个工具没有登录体系，"假装知道用户是谁"
比"坦诚地不知道"更糟。多人共用一台机器时按 `author` 过滤，免得拿到别人的树。

## 5. 一个实测踩到的坑

`orchestrator.get_tree()` 的返回值里**没有** `root_id` —— 它不是树的一部分，
而是查询参数。第一版直接把 `get_tree()` 的结果喂给 `progress()`，于是每条投递报告
都拖着一条"读不到 root_id —— 这份进度可能不属于你以为的那棵树"。

也就是说：**每一条报告都带一条假警报**。而假警报比没有警报更坏 —— 它会让真警报被无视。
判据里专门钉了"不许有这条假警报"（`test_h5` / `test_h2`），把补 `root_id` 的那一行
去掉就会红。

## 6. 变异测试

| 变异 | 结果 |
|---|---|
| 忘了补 `root_id` | ✅ H2 红（"读不到 root_id"的假警报） |
| 把取消/阻塞也算完成 | ✅ G2 两条红 |
| `ratio` 的 `null` 渲染成 0% | ✅ D1 红 |

## 7. 已知限制（如实写下）

* **"持续报告"是靠"每次被问时读实时状态"实现的，不是推送**。所以如果用户不问，
  管家不会主动开口。要不要主动开口属于 P3-5 的自动策略与已有的主动汇报开关
  （`steward_proactive_enabled`）的范围 —— 本次刻意不把两者耦合。
* 进度里**没有进度条式的时间估计**（"还需 20 分钟"）。本工具没有可靠的耗时模型，
  用时间外推会比节点计数更假（成本侧的时间外推同样被刻意排除，见 `docs/cost-accounting.md`）。
* 只跟踪**最近一次**投递的进度（可加 `author` 过滤）。同时推进多条目标时，
  面板只显示最新那条 —— 要看全部得走跨工程总览（P3-4）。
