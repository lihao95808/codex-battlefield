# 数据保留（P5-4）

实现：`api/app/retention.py`、`GET /api/retention`、`POST /api/retention/sweep`、
设置里的 `data_retention_days`（「自动策略」分组）。

判据：`api/tests/test_retention.py`（30 例）、`test_retention_api.py`（10 例）。

## 1. 这一层最危险的失效方向

ROADMAP 写得很直白：**"数据清理最容易悄悄破坏恢复能力"**。而且它的表现不是报错 ——
是**"某天真的需要恢复时才发现恢复不了"**。那一天通常离清理动作已经很久。

所以第一条规矩不是"删什么"，而是：

> **先列"不能删什么"**，并且这个清单要能从返回值里读出来。

`plan()` 返回 `protected`，每一项带理由。于是"我没有删掉不该删的"是**可核对**的，
而不是一句承诺。

## 2. 三种东西，三种待遇

| 类别 | 例子 | 待遇 |
|---|---|---|
| **重建得出来** | `runs/` 里的日志与提示词、`full_checkpoints/`、`checkpoint_ledger/`、`codex-home/` | 可以删（有保留窗口） |
| **删了就没了的** | 库里的表（任务树/宪法/事件/债务/…） | **永不删** |
| **还原锚点** | 每棵树**最新**的那份快照 | **永不删**（更早的才可以） |

判断标准只有一条：**删掉之后，还能不能从别处算出同样的东西？**

另外**工作树不归这里管**：`worktrees.decide()` 已经有它自己的保留期与指纹守卫。
两套清理规则作用于同一个目录，"到底是谁删的"在事故复盘里就查不清了。

## 3. 保留窗口

默认 **7 天**（保守：少留的那一侧不可逆），上限 365 天。
**0 是合法值** = "只留还原锚点"。

改法：设置面板的「数据保留（天）」，或配置文件 `data_retention_days`。

## 4. 两条实现上的坑（都是实测踩到的）

### 4.1 `0` 被当成"未设"

端点第一版写的是 `settings.data_retention_days or DEFAULT_RETENTION_DAYS` ——
`0 or 7` 得到 **7**。于是用户把窗口设成 0 之后，实际行为是"保留 7 天"，
而设置面板上显示的还是 0。**设了不生效，且没有任何报错。**

修法：区分"没设"（`None`）与"设成 0"。变异测试确认：改回 `or DEFAULT` 会让
`test_s4` 红（那次清理什么都没删）。

### 4.2 非法窗口让端点 500

`normalize_days` 会为越界值抛 `RetentionError`，那是**用户配置错**，必须当 4xx 报出去。
第一版没接住，`GET /api/retention` 在窗口配错时直接 500。

## 5. 判据里三条值得说的

| 判据 | 为什么 |
|---|---|
| **`R9` 清理之后快照还原仍然成功** | 这是 ROADMAP 那条判据本身。做法是造一份**真的能用的**快照，清理后**读回来比对** —— 只看"锚点文件还在"是自欺（它可能在，但已经读不出内容） |
| `R3` 源码级检查"不许出现删行/删表的 SQL" | 行为测试只覆盖它跑到的路径；"某天有人加了一句清理行的代码"是最容易悄悄发生的退步 |
| `R8` 读不到 mtime → 进 `unknown`，**不猜** | 猜"它大概很旧了"会删掉正在用的东西 |

## 6. 变异测试

| 变异 | 结果 |
|---|---|
| 锚点也进候选（不再受保护） | ✅ R1 两条 + R9 + S4 共 6 条红 |
| `0` 当成未设（`or DEFAULT`） | ✅ S4 红（清理没删任何东西） |
| 源码里出现 `DELETE FROM` | ✅ R3 红 |

## 7. 已知限制（如实写下）

* **没有后台定时清理**。现在是显式的 `POST /api/retention/sweep`。
  要不要定期自动清是一个策略决定（"无人看护时自动删数据"听起来就不太对），
  所以刻意留给显式调用 —— 需要的话由看门狗那侧决定何时调。
* `checkpoint_ledger/` 与 `codex-home/` 也在可清列表里，但它们**可能正在被使用**
  （当前正在跑的那次运行）。判断依据只有 mtime，**不检查是否有活进程持有** ——
  Windows 上被占用的文件会删失败并如实进 `failed`，Unix 上则可能删掉正在读的文件。
  这一条要做得更稳需要与进程扫描联动，属 P5-6 的范围。
* **没有量过真实的清理量**。本机的状态目录几乎是空的（各子目录 0 MB），
  所以"能省多少磁盘"这件事没有实测数字 —— 不编。
* 清理**不会** vacuum 数据库文件。SQLite 删行才需要它，而本模块不删行。
