# 花费：归因与预测的口径（P3-2 / P3-3）

实现：`api/app/cost.py`（纯计算 + 只读读库）、`GET /api/cost`、界面 `CostPanel`。
判据：`api/tests/test_cost.py`（纯计算）、`api/tests/test_cost_api.py`（真库接线）、
`web/src/costView.test.ts`（显示逻辑）。

## 1. 为什么这一层要单独写一份口径

因为**花费数字一旦偏乐观，用户就会去做别的事**（比如去睡觉）。这不是"显示不够
精确"的问题，而是"让人做出错误决定"的问题。所以这里的每条取舍都写明失效方向。

## 2. 两个问题、两套口径

| 问题 | 口径 | 刻意**不**做的事 |
|---|---|---|
| 钱花在哪一层（P3-3） | 已发生运行的用量，按节点/角色/模型拆 | 不把"没记录"渲染成一个桶 |
| 跑完还要多少（P3-2） | 已结算节点的**实际均价** × 剩余节点数 | 不猜模型单价、不假设剩余节点与已完成一样难 |

**与预算硬闸（P3-1）的关系**：P3-1 现在有四道闸，它们都发生在**发车点**（起 agent 之前）：
时间窗守卫、agent burst（按启动次数）、**树级 token 上限**、**树级金额上限**。
本模块管的是"这些车一共花了多少钱、接下来还要花多少"——它是**口径与报表**，不是闸门。
两者**有意分开**：闸门要在发车点做决定，报表要能解释"为什么是这个数"；
合成一个数会同时毁掉两边的可解释性（闸门用的是同一份归因，见下面那张表）。

⚠️ **2026-10-18 纠正一处口径，并在同一天补上了缺的那道闸**：P3-1 的 ROADMAP 行原来写
"token / 金额硬闸已落地"，核对代码后**不成立** —— 当时只有**时间窗**守卫
（`set_budget_guard(resume_after_seconds=…)` 把整树休眠到额度刷新）+ **agent burst**
（每个窗口允许起几个 agent），没有"这棵树花了多少就停"。后果是具体的：P6-4 的一轮真实递归
探针自己拆到 **6 层**、吃掉 **24.1M input tokens**，系统全程没停。

现在补上的那道闸：**`budget_token_ceiling`**（默认 `0` = 关）。

| 项 | 口径 |
|---|---|
| 统计 | `cost.cost_report(db, root_id)["attribution"]["total_tokens"]` —— 与 P3-3 归因**同一套规范化**，不另写一份 |
| 时机 | 每次**起 agent 之前**（`_reserve_agent_start` → `_hold_agent_start_for_token_budget`） |
| 触发 | 整树休眠（复用 `set_budget_guard`，24 小时窗口）+ 事件 `budget.token_ceiling`（带 used / ceiling / phase） |
| 放行 | 人工清守卫或预授权，**不是**自动把上限改大 |
| 代价 | 每次起 agent 扫一遍该树的 `run_records`（O(运行数)）—— 这就是它**默认关闭**的原因 |
| 判据 | `api/tests/test_budget_ceiling.py` B1–B6（B4 是接线判据：删掉钩子就红） |

**仍未做**：**金额闸**在同一天也补上了，但口径不同 —— 它必须先回答"我知道花了多少吗"：

| 情形 | 金额闸的行为 |
|---|---|
| 端点没自报金额（`cost_by_currency: null`） | **不暂停**，写 `budget.cost_unreadable` 说明原因 |
| 没配币种（`budget_cost_currency` 空） | **不暂停**，同一个事件 |
| 记过的是别的币种 | **不暂停**，写 `budget.cost_currency_absent` |
| 币种匹配且已超 | 整树休眠 + `budget.cost_ceiling`（带 used / ceiling / currency / `other_currencies`） |

为什么"读不到"不暂停：拿猜测的币种去暂停树是**误报**，而误报会让用户不再相信闸门；
但静默失效也不行，所以每种"没生效"的原因都落一条事件（同一棵树同一种原因只记一次）。
判据 `api/tests/test_budget_cost_ceiling.py` C1–C8。

**“跨币种换算”这条决定本身也有判据了**（C8）：配置的 CNY 只有 0.5（上限 5），而另有一笔 1000 USD —— 闸门**必须不暂停**。变异（把 `used` 改成 `sum(所有币种)`）→ C8 立刻红，失败信息直接点出“说明币种被相加或换算了”。
为什么不换算：换算需要汇率来源与口径（哪天、哪个牌价、谁维护），那是**新的外部依赖**；在没有它之前，宁可“只按你声明的那个币种算，其余单列给你看”，也不偷偷加总。


## 3. 四类"读不到"必须能被分辨

这是本模块存在的主要理由。它们各自指向**不同的用户动作**：

| 情形 | 上报方式 | 用户该做什么 |
|---|---|---|
| 供应商没报金额 | `cost_by_currency: null`（不是 `0`） | 查计价/网关配置 |
| 用量认不出来（字段名变了） | `runs_without_usage` 计数 + 界面提醒 | 查 provider 适配 |
| 没记录模型名 | `runs_unknown_model` 计数，**不进** `by_model` | 查 runner 的记录链路 |
| 还没有已结算节点 | 预测 `available: false` + "还没有样本" | 多跑几个节点 |

把其中任何一类显示成 `0`，用户就会得到"没花钱"或"不用再花"的错误结论。

**为什么不造假桶**：`model="unknown"` 这样的桶会让「47% 的花费属于 unknown」
看起来像一个统计结论（可以去优化），而真相是「这些运行没记录模型」（要去修记录）。
两件事的下一步动作完全不同。

## 4. 预测的算法与它不承诺什么

```text
unit   = 已结算节点的金额之和 / 已结算节点数        # blocked 不算，见 §5
low    = unit × 剩余节点数
mid    = low × retry_factor
high   = mid × 2
```

* `retry_factor` = `min(3, 1 + failed_and_canceled / 节点数)`，**有上界**：
  重试率再高，用 3 倍去吓人也不比"看事实"更有用。
* 单位是**节点**而不是小时：本工具没有可靠的耗时模型，用时间外推会更假。
* 单一币种：混币种时**拒绝给预测**并说原因，不做汇率假设（实测：忽略冲突会被用例抓住）。
* 样本量必须和数字一起出现；少于 5 个节点时界面明写"这个区间很粗，不能当作承诺"。

**不包含**：模型涨价、需求变更、人工返工、上游限流导致的额外等待。

## 5. 为什么 `blocked` 不算单价样本

`blocked` 是**终态**但不是"已结算"：它花过钱，却没有产出一个可用的工作单位。
把它算进均价会把 unit 拉低，于是预测偏乐观 —— 而乐观是这里最坏的方向。

实测（变异测试）：让一个花费 0.001 的 blocked 节点进入样本，unit 从 2.0 掉到 1.0，
`test_r1_blocked_nodes_are_not_used_as_price_samples` 立刻红。

`failed` / `canceled` **要**算：它们同样消耗了一个工作单位，是真实成本。

## 6. 已知限制（如实写下）

* 归因按**运行发生时**的记录；如果 `usage_json` 是后来才补上的（供应商异步回账单），
  历史运行会显示成"没报金额"。本模块不做事后对账 —— 那需要网关侧的账单接口。
* 一棵树跨多个 `constitution` 版本时，归因**不按版本再拆**。要回答"改宪法之后
  是不是变贵了"，目前只能靠时间窗口自己看。
* `by_node` 只按 token 排序时的顺序不保证跨运行稳定（同 token 时按 id）。
