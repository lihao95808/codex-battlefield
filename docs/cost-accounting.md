# 花费：归因与预测的口径（P3-2 / P3-3）

实现：`api/app/cost.py`（纯计算 + 只读读库）、`GET /api/cost`、界面 `CostPanel`。
判据：`api/tests/test_cost.py`（纯计算）、`api/tests/test_cost_api.py`（真库接线）、
`web/src/costView.test.ts`（显示逻辑）。

## 1. 为什么这一层要单独写一份口径

因为**花费数字一旦偏乐观，用户就会去做别的事**（比如去睡觉）。这不是"显示不够
精确"的问题，而是"让人做出错误决定"的问题。所以这里的每条取舍都写明失效方向。

## 2. 两个问题、两套口径

| 问题 | 口径 | 刻意**不**做的事 |
|---|---|---|
| 钱花在哪一层（P3-3） | 已发生运行的用量，按节点/角色/模型拆 | 不把"没记录"渲染成一个桶 |
| 跑完还要多少（P3-2） | 已结算节点的**实际均价** × 剩余节点数 | 不猜模型单价、不假设剩余节点与已完成一样难 |

**与预算硬闸（P3-1）的关系**：硬闸管"还允许发几次车"（按启动次数，在发车点拦），
本模块管"这些车一共花了多少钱"。两者口径不同且**有意保持不同** ——
合成一个数会同时毁掉两边的可解释性。

## 3. 四类"读不到"必须能被分辨

这是本模块存在的主要理由。它们各自指向**不同的用户动作**：

| 情形 | 上报方式 | 用户该做什么 |
|---|---|---|
| 供应商没报金额 | `cost_by_currency: null`（不是 `0`） | 查计价/网关配置 |
| 用量认不出来（字段名变了） | `runs_without_usage` 计数 + 界面提醒 | 查 provider 适配 |
| 没记录模型名 | `runs_unknown_model` 计数，**不进** `by_model` | 查 runner 的记录链路 |
| 还没有已结算节点 | 预测 `available: false` + "还没有样本" | 多跑几个节点 |

把其中任何一类显示成 `0`，用户就会得到"没花钱"或"不用再花"的错误结论。

**为什么不造假桶**：`model="unknown"` 这样的桶会让「47% 的花费属于 unknown」
看起来像一个统计结论（可以去优化），而真相是「这些运行没记录模型」（要去修记录）。
两件事的下一步动作完全不同。

## 4. 预测的算法与它不承诺什么

```text
unit   = 已结算节点的金额之和 / 已结算节点数        # blocked 不算，见 §5
low    = unit × 剩余节点数
mid    = low × retry_factor
high   = mid × 2
```

* `retry_factor` = `min(3, 1 + failed_and_canceled / 节点数)`，**有上界**：
  重试率再高，用 3 倍去吓人也不比"看事实"更有用。
* 单位是**节点**而不是小时：本工具没有可靠的耗时模型，用时间外推会更假。
* 单一币种：混币种时**拒绝给预测**并说原因，不做汇率假设（实测：忽略冲突会被用例抓住）。
* 样本量必须和数字一起出现；少于 5 个节点时界面明写"这个区间很粗，不能当作承诺"。

**不包含**：模型涨价、需求变更、人工返工、上游限流导致的额外等待。

## 5. 为什么 `blocked` 不算单价样本

`blocked` 是**终态**但不是"已结算"：它花过钱，却没有产出一个可用的工作单位。
把它算进均价会把 unit 拉低，于是预测偏乐观 —— 而乐观是这里最坏的方向。

实测（变异测试）：让一个花费 0.001 的 blocked 节点进入样本，unit 从 2.0 掉到 1.0，
`test_r1_blocked_nodes_are_not_used_as_price_samples` 立刻红。

`failed` / `canceled` **要**算：它们同样消耗了一个工作单位，是真实成本。

## 6. 已知限制（如实写下）

* 归因按**运行发生时**的记录；如果 `usage_json` 是后来才补上的（供应商异步回账单），
  历史运行会显示成"没报金额"。本模块不做事后对账 —— 那需要网关侧的账单接口。
* 一棵树跨多个 `constitution` 版本时，归因**不按版本再拆**。要回答"改宪法之后
  是不是变贵了"，目前只能靠时间窗口自己看。
* `by_node` 只按 token 排序时的顺序不保证跨运行稳定（同 token 时按 id）。
