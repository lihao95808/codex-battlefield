# Codex Battlefield 需求→证据追溯 SPEC

状态：执行中（spec 定稿 → 实现 → 自测）
续跑锚点：`PLAN-STATUS.md`

## 1. 动机（现状事实）

| 事实 | 含义 |
|---|---|
| 完成判据是"入站债务为空 + 整合验收通过"，而债务与验收都挂在**项目宪法**上 | 体系能保证"符合宪法"，**不能**保证"宪法符合目标"——目标本身没有可核对的覆盖计数 |
| 宪法是 markdown + 边界 JSON（`data.global_acceptance` 等），没有"每条原始要求 ↔ 可核对判据"的对应关系 | 漏掉一条需求，与"把这条需求做错了"，在现有体系里看起来一模一样：都没有信号 |
| 已有 `CONSTRAINT_COVERAGE_GAP_BLOCKS`（约束覆盖缺口会阻断） | 它是这条路的**种子**，但只覆盖"约束 vs 节点"这一层，没有回到**原始要求** |

目标一句话：让"漏需求"和"读错需求"第一次变成**可拦的东西**。

## 2. 非目标

- 不做自然语言理解（"这条需求到底在说什么"仍由模型判断）。
- 不要求把人写的原始需求自动切分——切分由宪法生成阶段产出，人可改。
- 不替换现有验收（Godot 门禁、成品门禁、债务门禁都照旧）；这是**加一层覆盖判据**。

## 3. 设计

### 3.1 声明的形状（宪法 `data.requirements`）

```json
{
  "id": "R1",
  "text": "击杀后必须回到待机状态",
  "criteria": [
    { "id": "c1", "type": "contains", "path": "scripts/player.gd", "pattern": "state = IDLE" },
    { "id": "c2", "type": "command", "command": ["{python}", "tools/check_idle.py"], "expect_exit": 0 }
  ]
}
```

- **判据词表与能力基准共用一处**（`app/bench.py` 的 `evaluate_check`：`file_exists` / `contains` /
  `not_contains` / `command`）。同一语义两份实现必然漂移——这是 W3 的教训。
- 判据一律相对**根目标**求值；绝对路径与 `..` **不判定**（不是"通过"）。

### 3.2 覆盖判据（这是本条的核心）

| 情况 | 严重度 | 理由（失效方向写明） |
|---|---|---|
| 声明了要求，但**没有任何可核对判据** | **blocking**（`requirement_uncovered`） | 这正是"漏需求"：没有判据的要求等于没有要求 |
| 判据**没过** | **blocking**（`requirement_unmet`） | 这是"没做到" |
| 判据**判不了**（读不到 / 命令超时 / 路径越界） | **不判定**（单列 + 事件） | 判不了 ≠ 没做到；一次文件占用不该拦下整棵树 |
| 要求**全部**有判据且全过 | 清债（按事实） | 与 R5/B 同源：可核对的事实，不是"谁完成了什么" |
| 宪法**没声明** `requirements` | **不判**，但看板/事件必须显示"未声明要求矩阵" | 不许把"没声明"读成"已覆盖" |

- 幂等键绑**要求 id / 判据 id**（不绑"谁改的"），与 R5/B 同源，避免修复子任务制造新 id 的无限增长。
- 进 `REVIVABLE_TYPES`：要求矩阵在人工修订后重声明（requirements 变化）属于"另一件事"。

### 3.3 接线位置

在父节点验收尾、`_obligation_gate` 之前，紧跟验收面篡改门禁：

```
_record_acceptance_surface_obligations   # 裁判被动过吗（B）
_record_requirement_obligations          # 需求都被判据覆盖且过了吗（A）
_record_regression_obligations           # 产物有没有回退（R5）
_obligation_gate                         # 既有的唯一门禁
```

顺序的理由：先问"裁判有没有被动手脚"，再问"它判的东西覆盖全不全"，最后问"产物有没有坏"。

### 3.4 已知限制（如实写下）

- 覆盖判据只能证明"**声明的**要求都被判据覆盖"，不能证明"声明的要求就是原始需求"——
  最后那一跳仍是人的责任（宪法修订要 `actor`）。
- 判据是文本/命令级的，语义级等价（换一种实现但同样满足需求）取决于判据写得够不够"行为化"
  （与能力基准同一条建议：能用行为判据就别用文本判据）。

## 4. 验收（可反驳）

| 编号 | 判据 | 怎么反驳 |
|---|---|---|
| T1 | 要求没有判据 → 父节点**不得** `done`，债务 `requirement_uncovered` 且理由**点名要求 id** | 声明一条无判据的要求跑验收 |
| T2 | 判据没过 → 不得 `done`，债务 `requirement_unmet` 点名要求 id 与判据 id | 把判据写成必然失败 |
| T3 | 判据**判不了** → **不**阻断，但事件写明"未判定" | 用越界路径 / 读不到的文件 |
| T4 | 判据全过 → 要求清债、节点可 `done` | 正常路径 |
| T5 | 没声明 `requirements` → 不判、不加债（且如实显示未声明） | 不带 requirements 跑一遍 |
| T6 | 不改既有行为：`pytest` 0 failed 且 passed 数不降 | 与 A1 同门槛 |
