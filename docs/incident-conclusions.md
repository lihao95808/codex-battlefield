# 结论文档（P4-5）

实现：`api/app/conclusions.py`（抽取 + 渲染 + 落库）、`GET /api/conclusions/draft`、
`GET/POST /api/conclusions`、`GET /api/conclusions/{id}/export`、界面 `ConclusionPanel`。
判据：`api/tests/test_conclusions.py`（27 例）、`test_conclusions_api.py`（15 例）、
`web/src/conclusionView.test.ts`（11 例）。

## 1. 它解决的不是"事件存不存"，而是"当时为什么"

事件表记的是**发生了什么**，它答不了"**当时为什么这么决定**"。而后者恰恰是复盘时
唯一真正需要的东西 —— 事后看到一条 `cancel_node`，光看事件永远不知道那是不是个
合理决定。

所以一份结论由两部分拼成：

| 部分 | 谁产生 | 内容 |
|---|---|---|
| 事实 | **代码**（从库里抽） | 影响面、决策点时间线、代价、未清债 |
| 判断 | **人**（管家起草、你改） | "当时为什么这么决定" |

## 2. 与 `failure_retrospective` 的分工（容易混，写明）

| | 谁写 | 粒度 | 去哪 |
|---|---|---|---|
| `failure_retrospective` | 代码自动 | 单个失败/阻塞节点 | 上浮给父节点当**提示词材料** |
| 结论文档（本模块） | 人 | 一棵树 / 一次事故 | 归档，供人读 |

前者喂给模型，后者喂给人。混在一起的后果是"给人看的东西被模型的提示词需求牵着改"，
两边都不好用。

## 3. 三条设计规矩

### 3.1 事实与判断分段

Markdown 里 `## 影响面（代码抽取）` / `## 做了什么决定（代码抽取的决策点）` /
`## 代价（代码抽取）` / `## 当时为什么这么决定（**人写**）` 是分开的段。
混合渲染后读者分不清哪句是数据、哪句是猜测，而复盘最怕的就是这个。

### 3.2 空段 ≠ 没有

每段都可能是"读不到"或"那类事件压根没发生"。所以草稿必须带
`## 这份草稿里没能确定的地方`：

* 时间线是空的 → 写进"没能确定"，并**同时给出两种可能**（确实没做过决定 / 决定没被记录）；
* 花费读不到 → 写进"没能确定"，并明说"不代表没花钱"；
* **没有未清债 → 不写**（"没有欠账"是一个确定的事实，不是缺失）。

把最后这条也写进缺失，会让每份干净的结论都拖着一条"没能确定"，于是没人再认真读那一段。

### 3.3 只有人写的才算结论

`write()` 要求非空的 `authored`，否则 400。一份只有自动事实的文档不值得归档 ——
它只是另一份事件表，**而且会因为"看起来像结论"而更少被人重新检查**。

## 4. 决策点的筛选口径

时间线**只收决策事件**，不收全部事件。口径是**可解释的**（一份词表），
不是按严重程度打分 —— 打分会让"为什么这条在里面"变得说不清。

词表在 `conclusions.DECISION_EVENT_TYPES`，覆盖：宪法锁定/修订、验收面冻结、
门禁阻断与升级、人工清债、人工介入、重试、取消、休眠与恢复、预算闸、
机器安全守卫、自动并发调整、看门狗重排队、API 重启排空。

注意**全局事件也要收**（`task_id` 为空的那种）：宪法锁定、人工清债这类决策常常
不属于某个节点，漏掉它们正好漏掉最该进时间线的东西。

## 5. 两个刻意的"不做"

* **草稿不落库**。`GET /api/conclusions/draft` 每次都现算。草稿是给人改的中间产物，
  每次点一下就落一条的话，归档区很快会被草稿塞满，"归档"也就失去意义了。
* **写结论不受管家只读限制**。`steward_read_only` 默认是开的，但写结论**不走那道闸** ——
  只读禁的是"替用户动树"，而归档一份文档不动任何东西。要求先关只读才能记录复盘，
  结果只会是没人记录复盘。

## 6. 变异测试（证明判据能红）

| 变异 | 结果 |
|---|---|
| 空时间线不进 `incomplete` | ✅ K1 红 |
| 不筛决策点（全部事件进时间线） | ✅ 3 条红（含"别的树的事件混进来"） |
| 允许空 `authored` 落库 | ✅ 2 条红 |

## 7. 已知限制（如实写下）

* **结论不参与任何门禁**。它是一份文档，不是判据 —— `final` 只表示"人已经看过并定稿"，
  **不表示结论正确**。想让"事故必须有结论"成为硬约束的话，那要另加一条债务类型，
  目前刻意不做（会变成又一个可以糊弄的勾选项）。
* 草稿的决策点上限是 40 条（`TIMELINE_LIMIT`），超出只留计数。文档是给人读的，
  长了就没人读 —— 但这也意味着**很长的历史会被截断**，需要完整时间线时得直接查事件表。
* 代价只从 `run_records` 的用量记录算，**不含**人工排查的时间成本。
* 导出是单文件 `.md`，没有打包相关日志/产物的能力（那属于 P2-4 诊断包的职责范围，
  两者刻意分开：诊断包给"别人帮你看"，结论给你自己归档）。

## 8. 本次顺带发现的两条假失败（未引入、但被本次全量跑暴露）

整套跑（`-n auto`）偶发红、单跑必绿 —— 典型的假失败。假失败的代价不是"麻烦"，
而是**真正的回归会淹在噪声里**。已处理/已记录：

### 8.1 已修：`test_concurrency.py::test_orchestrator_delegates_agree_with_module`

`auto_concurrency_fuel_state` 里有 `minutes_to_deadline` 与 `deadline_elapsed`
两个**分钟级**时钟量；"orchestrator 的委托 == 模块函数"这条判据连续调用两次，
跨过分钟边界时两边给出不同字典。

**修法**：用 `monkeypatch` 把 `concurrency.utcnow` 冻在一个固定时刻。
比"加个 retry 容忍一下"更好：冻住时钟后两边看到的是同一时刻，
差异只可能来自实现 —— 判据反而**更严**了。

### 8.2 已记录（未修）：`test_godot_slot_capacity.py::test_godot_slot_capacity_limits_concurrency`

症状：`PermissionError: [Errno 13] ... godot.resource.state.json`。

成因是 **Windows 文件锁竞争**：该用例起 3 个真实进程去抢 Godot 槽位（容量 2），
多个进程同时写同一个 `godot.resource.state.json`；并发写入者持有句柄的瞬间，
另一方的 open 就吃到 Errno 13。这是**产品侧的写竞争**（不是测试写法问题），
但在 CI 的高并发下比在单机手动跑更容易命中。

不现在修的理由：它是**产品代码的并发写**，要么给状态文件加原子重命名写入、
要么让写入串行化 —— 那是一次真实的运行时改动，应当有独立判据，
不该顺手塞进 P4-5。**记在这里而不是忽略**：下次有人看到这条红时能直接对上。
