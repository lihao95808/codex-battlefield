# 自动策略：看得见的自动（P3-5）

实现：`api/app/auto_policy.py`（纯判定）、`GET /api/auto-policy`、界面 `PolicyPanel`。
判据：`api/tests/test_auto_policy.py`（26 例判定）、`test_auto_policy_api.py`（10 例接线）、
`web/src/policyView.test.ts`（17 例显示）。

## 1. 要解决的不是"能不能自动"，而是"自动得看不看得见"

系统里本来就有这些动作（停止重试、降并发、休眠），但它们散在各处，**没有任何地方
能回答**：

* 现在有哪几条自动策略？各自开着吗？
* 它上一次为什么触发 / 为什么没触发？

第二个问题里最要紧的是第三种情况：**"策略关掉了"与"策略没到条件"原本看起来完全一样**。
前者意味着用户以为有保护其实没有 —— 而他不会去查。

所以每条策略都：具名、带"为什么存在"的理由、把**开关状态**与**没触发的原因**
一起进报告。

## 2. 四条策略

| 策略 | 触发条件 | 动作 | 为什么需要 |
|---|---|---|---|
| 连续失败自动停 | 同一节点连续失败 ≥ 上限（默认 3，可配） | `stop_retrying` | 同一节点用同样的提示词反复失败几乎总是**信息缺失**，不是运气不好；继续烧钱只会把信号埋掉 |
| 收益递减自动降并发 | 最近一个窗口（10 次）**零成功** | `lower_concurrency` | 当前并发下 agent 在互相挤或都踩同一类错误；加并发只会让失败更快更多 |
| 空闲自动休眠 | 无活跃 + 无排队 + 闲置超阈值（三条同时） | `hibernate` | 树会长期停在"等人"（阻塞债、等额度），占着槽位与内存没有意义 |
| 僵死槽位回收 | 有活进程但超 900s 无进度 | `reclaim_slots` | 降并发是"少发车"，这条是"把占着车位却熄火的车拖走"；少了它几个僵死槽位会吃光并发额度，而看板显示的是"在跑" |

四条都在设置面板的「自动策略」分组里，可单独关闭。

## 3. 三条硬规矩

### 3.1 失效方向偏保守：拿不到数据一律**不触发**

四种情况都会返回 `fired=false` + "缺什么"：开关关闭、数据不足、键缺失、值类型不对。
**少触发一次最多是少省一点；误触发会打断一次正常的长跑。**

具体到两条容易写错的：

* **空闲判定**：拿不到"最后一次活动时间"时**不给** `idle_seconds`（而不是给 0）。
  给 0 的话"0 ≥ 0"立刻成立 → 立刻休眠整树。
* **僵死槽位**：`has_process` 不给就是 `False`（不猜"大概还有进程"）。猜错的代价是
  把真在干活的 agent 的槽位回收掉。

### 3.2 判定是**纯函数**，快照由调用方给

`evaluate(observation)` 不读库、不看时钟。`observe()` 也只吃**已经取好的树快照**。

这条最初写错过：第一版让 `observe(db, root_id=...)` 自己去查树，被
`tests/test_module_layering.py` 的 C2 判据当场抓住（`auto_policy: ['models', 'orchestrator']`）。
修法不只是"把 import 挪进函数"——**更重要的是"策略看到的是哪一份树"必须由调用方决定**：
它自己去查一次，就会和同时刻的看板/动作读到两份快照，而策略的判定依据事后无法复盘。

### 3.3 动作由调用方执行，本模块**只判定**

`ACTIONS` 是封闭词表（`stop_retrying` / `lower_concurrency` / `hibernate` / `reclaim_slots`）。
自动策略不会变成第二套并发控制 —— 两套并发控制互相打架是这里最容易犯的错。

## 4. 覆盖率与变异测试

| 变异 | 结果 |
|---|---|
| `policyStatus` 忽略 `enabled`（"已关闭"伪装成"守护中"） | ✅ 前端用例红 |
| 连续失败判据 `>=` 改成 `>`（边界差一次） | ✅ A2 / N1 红 |
| `recent_results` 不按时序（取成最早那批） | ✅ N2 红 |
| 让 `observe` 自己查树（反向依赖 orchestrator） | ✅ C2 分层判据红 |

## 5. 已知限制（如实写下）

* 本模块**只报告判定**，实际动作的执行仍在编排层。也就是说：报告说"该回收了"
  不等于"已经回收了"。`fired` 的语义是"条件成立"，不是"动作已执行"。
* `has_process` 依赖节点的 `node_meta.external_process_alive`，目前只有部分路径会写它。
  拿不到时僵死槽位策略恒不触发（偏保守），但这也意味着**它在多数运行里其实是沉默的**。
  要让它真正干活，得先把进程扫描的结果写进那个字段 —— 那属于 P5-1 的接线范围。
* 报告是"某一刻的判定"，不保存历史。要回答"昨天它触发过几次"目前只能查事件表。
