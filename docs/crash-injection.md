# 崩溃注入与还原锚点（P5-6）

实现：`api/app/checkpoint.py`（`atomic_write_json` / `atomic_write_text` / `_replace_with_retry` /
`read_state_snapshot` 的备份回退）、`orchestrator._write_state_snapshot` 改用原子写。
判据：`api/tests/test_crash_injection.py`（23 例）。

## 1. 这一层真正要保的是什么

ROADMAP 的判据是**"崩溃注入下'不丢已验收结果'可复现"**。对当前架构来说，
"已验收结果"的持久化有两处：

| 落点 | 内容 | 崩溃风险 |
|---|---|---|
| SQLite（`battlefield.sqlite3`） | 任务树、状态、事件、债务 | **低**：SQLite 的 WAL + 事务本身就保证原子提交 |
| `state_snapshots/<root>/latest.json` | **还原锚点** | **高**：原本是 `write_text`（截断后写），进程在写它的中途被杀就留下半截文件 |

第二行才是问题所在，而且它的失效方向是最坏的：

```
  崩在写锚点的中途
        │
        ▼
  半截 JSON（解不出来）
        │
        ▼
  _restore_snapshot_if_missing 读到 None → 返回 None → **静默放弃还原**
        │
        ▼
  "表被清空"那条通路恰好在最需要它的时候失效，而且没有任何报错
```

## 2. 三层修复

### 2.1 原子写（`atomic_write_json`）

三步，缺一不可：

1. **先把当前那份（能解出 JSON 的）复制成 `.backup`** —— 崩溃时的退路。
   解不出来的旧文件**不备份**（备份一个坏锚点等于把唯一的好副本覆盖掉）。
2. 写一个**每个写者唯一**的临时文件（进程号 + 随机段），再 `os.replace` 进去。
   共享的 `<name>.tmp` 会让两个写者互相踩 —— 这一条在 P4-2 的 Godot 状态文件上
   已经实测过一次（一方 replace 后另一方 Errno 13，而调用方的 `except` 把它
   静默吞掉，那次更新完全没发生）。
3. 换名**带有限次重试**（约 0.3 秒后放弃）：Windows 上目标文件被读者打开时
   `os.replace` 会失败。这也实测过。

`os.replace` 保证读者只会看到**旧内容或新内容**，不会看到半截。

### 2.2 读者退备份并**出声**

`read_state_snapshot` 主文件解不出来时退到 `.backup`，并往 stderr 打一行。
**出声这一点是有意的**：静默用备份会掩盖"真的丢过一次写"——
而那次丢写可能意味着别的东西也没写下去。

### 2.3 历史快照是尽力而为

历史快照（带时间戳的那份）写失败不该让主锚点的写成功被抹掉，所以它单独
`try/except` 包住。实测依据：同一微秒内两次写会撞名，撞上时 Windows 会报错。

## 3. 崩溃注入怎么做的

**不是在外部随机杀**——随机杀会以极高概率落在"什么都没发生"的时刻，于是判据绿得毫无意义。

做法是在真实写入路径的**每个阶段**各埋一个硬杀点，用子进程 + `os._exit(9)`：

| 阶段 | 模拟的崩溃时机 |
|---|---|
| `after_backup` | 备份写完、新内容还没写 |
| `mid_temp_write` | 临时文件写到一半 |
| `before_replace` | 临时文件完整、还没换名 |
| `after_replace` | 换名完成、还没返回 |

**为什么必须 `os._exit` 而不是抛异常**：异常会被 `except OSError` 接住并清理 ——
那就测不到"被杀"了。崩溃注入必须是**不给清理机会**的那种死法。

对每个阶段都断言两件事：**主锚点读得出来**（不是"文件还在"——半截文件也在，
但它等于没有），且内容**要么是旧版本、要么是新版本**。

另有一条两进程并发写：写者跑的同时反复读，读者看到半截就红。

## 4. 一条被变异测试救回来的判据

接线判据最初写的是：

```python
assert "atomic_write_json" in source        # ❌ 太弱
```

变异测试把它改成 `atomic_write_text(...)`（**不带备份**的那条路）之后，
**判据照样通过** —— 也就是说那条判据是空的。

改成完整调用：

```python
assert "checkpoint.atomic_write_json(latest_path, payload)" in source   # ✅
```

改完立刻红。教训：**源级判据要断完整的调用，不要只找一个函数名的子串** ——
同族函数的名字往往共享前缀，子串匹配会把"用错了哪一个"放过。

## 5. 变异测试记录

| 变异 | 结果 |
|---|---|
| 换名不重试（去掉 `_replace_with_retry`） | ✅ C5 并发写红（两个写者之一报错） |

## 6. 已知限制（如实写下）

* **`taskkill` 那条已经补上了**（2026-10-18，§7）：对**真实** Codex 进程树（`cmd.exe → node → codex.exe`，7 个进程）实测 —— 杀完 5 秒内 0 个存活、被杀的调用带失败返回；把杀换成 no-op 的变异会红。默认 skip（会花额度），设 `CODEX_BATTLEFIELD_REAL_PROCESS_KILL=1` 才跑。**仍然没有**的是"杀毒软件/受限权限环境下 `taskkill` 会不会被拦"这一类环境差异（本机没有那个环境）。
* **没有测"断电"**（真正的掉电无法在测试里模拟）。用 `os._exit` 模拟的是
  "进程立刻消失、不做任何清理"，这与断电对**文件系统缓冲**的影响不完全一样
  （掉电可能丢掉已 `write` 但未 `fsync` 的数据）。要真覆盖掉电需要 `fsync` 语义
  与文件系统级别的注入，不在本次范围。
* **`fsync` 没有显式调用**。`os.replace` 保证可见性切换的原子性，但"换名之后掉电
  是否还在"取决于文件系统与操作系统。要求更强的一致性需要 `fsync` 目录项 ——
  那是另一个量级的取舍（每次写快照都 fsync 会明显变慢），本次不做，如实记下。
* `.backup` **只保留一份**（上一次成功的）。更早的历史由带时间戳的历史快照承载，
  而它受 P5-4 的保留窗口管辖。

## 7. 补上"另一半"：对**真实** Codex 进程树的那一刀（2026-10-18）

§6 把 `taskkill` 这条记为"没验"。现在补上了，判据在
`api/tests/test_external_process_kill.py`（默认 **skip**，因为会真的调一次 Codex CLI；
设 `CODEX_BATTLEFIELD_REAL_PROCESS_KILL=1` 才跑，skip 时把原因写在 skip 消息里）。

### 7.1 为什么这件事不能只靠 mock

真实 Codex 的进程形状是 **`cmd.exe`（npm 的 `.cmd` 转发器）→ `node` → `codex.exe`**，
本机实测这一棵树有 **7 个进程**。只杀父进程会留下孤儿 `codex.exe`，而孤儿继续占 Codex 槽位 ——
这正是本轮早些时候"树一步都走不动"的同一个故障面（事件
`scheduler.external_codex_slots_full`）。所以"杀完没有孤儿"必须对着真实进程形状量。

### 7.2 怎么验

1. 用 `CodexExecRunner._run_codex_io` 起一次**真实**调用（隔离 cwd，`--cd` 指到临时目录）；
2. 从 `asyncio.create_subprocess_exec` 出来的 `process.pid` 拿到父进程，用 WMI 展开整棵子树；
3. **先断言这一棵此刻都活着**（否则"杀完都没了"可能只是它们自己跑完了）；
4. 调产品自己的 `Orchestrator._stop_external_codex_process_tree(pid)`；
5. 断言：`stopped=True`、5 秒内子树上每个 pid 都不在了、被杀的调用**带着失败返回**。

提示词刻意要一个**长回答**（`reason` 至少 800 字），让进程在 3 秒时一定还在跑。

### 7.3 结果

| 项目 | 实测 |
|---|---|
| 进程树规模 | **7 个**（`cmd.exe` → `node` → `codex.exe` 链） |
| 杀之前 | 7 个全部 `_alive()` |
| `_stop_external_codex_process_tree` | `stopped=True`、`exit_code=0` |
| 5 秒后存活 | **0 个** |
| 被杀的调用 | `exit_code != 0`（关掉重试后） |
| 用例耗时 | 11–14 秒 |

### 7.4 变异（两次，结论不一样，都记下来）

| 变异 | 结果 | 说明 |
|---|---|---|
| 把 `taskkill /T` 的 `/T` 去掉 | **仍然绿**（无孤儿） | 这个形状下 `/T` **不是必要条件**：父进程一死，`node` 读到 stdin EOF 自己退，`codex.exe` 跟着退。所以本用例证明的是**结果**（杀完无孤儿），不是"必须带 `/T`" —— 不要把它当成 `/T` 的判据 |
| 把整段杀进程换成 `return {"stopped": True}`（no-op） | **红**：7 个进程全活着（失败信息里列出全部 pid） | 这条变异才是本用例真正的假阳性防线：杀不动就会当场红 |

### 7.5 一条把断言写错过的实测（留着当教训）

第一次跑时"被杀的调用必须带着失败回来"这条**红了**，但 `exit_code=0`、`output_tokens=2709` ——
不是杀失败，而是 **runner 把"进程被杀"当成可重试失败，第 2 次尝试完整跑完了**。
也就是说：**杀掉一次真实调用，默认行为是"自动重试一次"**，这本身是对的（用户网络抖动时同理），
但验证"这一刀"必须先把 `codex_retry_attempts` 设成 0，否则量到的是重试而不是杀。
