# Codex Battlefield 任务间隔离 SPEC（R2）

状态：执行中（spec 定稿 → 实现可做部分 → 把做不到的部分写成显式未实现项）
前置：`docs/spec-resource-governance.md` §4 的 R0 实测（E1–E9）——本 spec 建在它上面，不重复实验
续跑锚点：`PLAN-STATUS.md`

## 1. 目标与真话

目标（用户口径）：**同一账号下，节点之间互不越权**——不读对方凭据、不写对方边界、不读对方产物。

R0（`spec-resource-governance.md` §4）当时的结论是"读隔离 codex 沙箱不提供、必须落 OS 层（Windows ACL）"，
并推断"同一账号下 ACL 才是唯一出路"。**2026-09-22 用当前 CLI 重测，R0 那条被推翻了**，见 §2.0。
ACL 那条路仍然说不通（ACL 的粒度是用户/组，不是进程），但它**不必要**了——**沙箱自己就把读限在 `--cd` 之内**。

| 想要的效果 | 现状（2026-09-22 实测） | 靠什么 |
|---|---|---|
| 不写对方边界 | **做到** | `--cd <自己的工作树>`（R0-E1/E2 + 本 spec 断言"命令行里没有 `--add-dir`"） |
| 不读对方**产物** | **做到**（本轮实测翻转 R0） | codex 沙箱把读限制在 `--cd` 根内：读 `node-b/secret.txt` → `Access is denied` |
| 不读对方**凭据（磁盘）** | **做到** | 每节点隔离 `CODEX_HOME`（§2.1），该目录里没有 `auth.json` |
| 不拿到**宿主上无关的凭据** | **做到**（本轮新增） | 子进程环境**默认收窄**（§2.4） |
| 网络出网控制 | **做不到** | 不属"同账号越权"；`frozen_mode` 之外没有网络层手段（§3） |
| 凭据不进子进程环境（`env_key` 模式） | **做不到** | 凭据只能经环境变量下发（§3） |

> ⚠️ **上表第 2 行（"不读对方产物"）有一个必要条件：codex 沙箱必须真的在跑。**
> 它靠的是 `--sandbox read-only / workspace-write`，**不是我们的代码**。
> 本机（2026-10-14 四组合实测）受限令牌建不起来：
> `CreateProcessAsUserW failed: 5 (拒绝访问。)`；全局 `[windows] sandbox = "elevated"`
> 又会让 helper 起不来（`helper_unknown_error: setup refresh had errors`）。
> **只有 `danger-full-access` 能跑通**——而那一档**关掉了沙箱**，于是这一行在本机**不成立**：
> 节点进程以同一用户身份运行，能读兄弟节点的工作树。
> 这是"能跑"与"隔离"之间的真实取舍，不是可以绕过的配置问题：
> ACL 的粒度是用户/组而非进程，同账号下没有可行的 OS 层补救。
> 所以本行在本机的正确读法是：**"设计上做到，但本机运行配置下失效"**。
> 沙箱档由 `CODEX_BATTLEFIELD_CODEX_SANDBOX_*` 控制（见 `docs/provider-setup.md`）。

### 2.0 读隔离：翻转旧结论的那次实测（2026-09-22）

`scripts/verify_isolation_boundary.py` 段 1 在 `node-a` 下用真实 CLI（`codex-cli 0.154.0`）读 `node-b/secret.txt`：

```
{"type":"item.completed","item":{"id":"item_1","type":"command_execution","command":"... Get-Content -LiteralPath 'G:\\...\\node-b\\secret.txt'","aggregated_output":"Get-Content : Access is denied\r\n...","exit_code":...}}
{"type":"item.completed","item":{"id":"item_2","type":"agent_message","text":"做不到。读取 `...\\node-b\\secret.txt` 时被拒绝访问，当前沙箱只允许读取工作区 `node-a`。"}}
```

- 结论：**沙箱把可读范围限在 `--cd` 根内**。节点的 cwd 是自己的 worktree，所以"读兄弟节点产物"这条路
  在默认配置下是**关闭**的。
- 前提条件（缺一不可，都有测试或断言守着）：节点的 cwd 必须是**它自己的 worktree**；
  命令行里**不得**出现 `--add-dir`（`--add-dir` 是精确扩展，加了就会把别处打开）。
- **与 R0 的差异如实记录**：R0-E3 测的是"跨目录读取全部放行"。差异的原因**未能确认**
  （可能是 CLI 版本变化，也可能是当时实验的沙箱参数/路径形态不同）。所以这里并排放两条带日期的读数，
  不改写旧记录；**当前行为以本轮实测为准**（它用的正是产品实际启动命令的形状）。

## 2. 实现（本波要做的四件）

### 2.0 前提：节点的 cwd 与"不加 `--add-dir`"

读隔离完全建立在"cwd = 自己的工作树"这个前提上，所以这两条要有断言守着（§4-I2、I7）。

### 2.1 每节点隔离 `CODEX_HOME`

- 现状：`settings.codex_home` 是**全局**一个（Hub 模式用它指向隔离配置）；所有节点共享它。
- 改成：节点进程拿到的是 `<codex_home>/nodes/<node-id>`。收益：会话/缓存/插件状态**互不可见**，
  一个节点写坏自己的 `CODEX_HOME` 不会影响兄弟；且（R0-E4）该目录里**没有** `auth.json`。
- **不夸大**：凭据若由 `env_key` 承载，它仍在**子进程环境变量**里（R0 已写明这一点），
  这一条治不了环境变量——它治的是"磁盘上的共享凭据与会话状态"。
- 目录在注入前创建；`CODEX_HOME` 未配置时**不注入**（不凭空造一个 home，行为与今天一致）。
- ⚠️ **与 provider 配置的相容点（2026-10-14 补，实测事故）**：codex **不从父目录继承
  `config.toml`**。只做上面这一步，节点 home 里的配置就是空的，`model_provider`
  整段丢失、请求回落到 `api.openai.com` 并 401。
  因此 `_codex_env` 必须同时调用 `_seed_node_home_config`，把基座 `config.toml`
  **每次覆盖**写进节点 home。**隔离与自定义 provider 这两件事只有这一个相容点**；
  漏掉它的表现不是报错停机，而是"树照跑、只是全打错端点"。
  详见 `docs/provider-setup.md` §2.1；由 `api/tests/test_node_home_config_seed.py` 的 S1–S5 钉住。

### 2.2 写边界的可核对化

- 现状：runner 不加 `--add-dir`（R0 结论：加了也不会越界到兄弟，但没必要）。
- 改成：`_codex_exec_args` 里显式**不**允许任何 `--add-dir`；并加一条测试断言命令行里没有它。
  （"我们没有加"与"我们保证不加"是两件事，后者可被测住。）

### 2.3 跨节点泄露检测（侦探）

- 口径：节点自己的 run 产物（last_message / worker 结果文本）里出现**兄弟节点的工作树路径**
  或**兄弟节点 id 的工作树形态**→ 记一条 **advisory** 债 `cross_node_leak`。
- 严重度：**advisory**，不是 blocking。理由（失效方向）：文本里出现一个路径**不等于**真的读了它
  （可能是它自己在日志里复述了父节点的提示词、或是集成目标里的合法引用）。advisory 让它可见、
  可排查；blocking 会拿猜测去拦一棵正在跑的树。
- **不误报**：自己的路径、根集成目标路径都必须排除；只做**精确路径匹配**，不做模糊包含。
- 幂等键绑 `(节点, 命中形态)`，与 R5/B/A 同源。
- 已知限制：它只能看见**我们记录的**文本（stdout/结果），看不见 agent 的内存态，
  也看不见"读了但没写下来"。它是证据，不是防线。

### 2.4 子进程环境收窄（本轮新增）

- 现状（实测证据，`verify_isolation_boundary.py` 段 2 打印）：`dict(os.environ)` 会把宿主上**与此无关**的
  凭据原样交给每个节点——实测看到 `<env_key>`、`provider`、`provider`。
  那是"节点能拿到不该有的凭据"，正是 R2 要治的一条。
- 改成：`settings.codex_env_strict`（默认**开**）→ 只保留系统/运行时必需键（固定名单）+
  代理/证书/包管理前缀 + 按前缀放行的凭据（默认 `CODEX_,OPENAI_,AZURE_OPENAI_,ANTHROPIC_`（可用 `CODEX_BATTLEFIELD_CODEX_ENV_ALLOW_PREFIXES` 加你自己的前缀））。
  实测环境从 100+ 键收到 **54** 键；**并且用真实 CLI 验证过它照样能跑**（段 4：退出码 0、回答了 `OK`）。
- ⚠️ `provider_` 是 2026-10-14 补进默认名单的：Hub 模式的隔离 `config.toml` 用
  `env_key = "<env_key>"`，漏掉它等于**把凭据自己过滤掉**，表现为节点全部 401。
  判据是"`env_key` 指名的变量必须下发"，不是"带 KEY 的都算无关"。
  由 `test_node_home_config_seed.py::test_e1_...` 做端到端接线断言（而非只断言常量）。
- 失效方向：**判不了就丢**（fail-closed）。要回到老行为：`CODEX_BATTLEFIELD_CODEX_ENV_STRICT=0`。
- **这次收窄的直接风险已经量过**：少了某个键的表现是"真实 Codex 起不来"，所以段 4 就是为它写的。

## 3. 未实现项（如实写下，不指望读者自己发现）

| 项 | 为什么没做 | 要真做需要什么 |
|---|---|---|
| 环境变量里的凭据对节点可见 | `env_key` 模式下凭据**只能**经环境变量下发（R0 §4 边界 3），而 2.4 的收窄只保证"**无关**凭据不下发" | 短期凭据 + 用完即失效的注入通道（需要凭据服务，不在本项目范围） |
| 网络出网控制 | 与本 spec 的"同账号越权"不是同一个问题 | 防火墙/代理策略；`frozen_mode` 只读之外没有网络层手段 |
| 沙箱之外的读路径（如 `--add-dir` 或未来 CLI 改变行为） | 读隔离依赖 codex 沙箱的行为，**不是我们的代码** | 升级 CLI 后重跑 `verify_isolation_boundary.py` 段 1（已留脚本） |
| 经环境的**间接**泄露（节点把兄弟内容抄进自己的产物） | 预防做不到（那已经不是"读"，是"写"） | §2.3 的侦探只给证据；要拦就得比对产物指纹 |

## 4. 验收（可反驳）

| 编号 | 判据 | 怎么反驳 |
|---|---|---|
| I1 | 节点进程的 `CODEX_HOME` 是**每节点**独立目录（含 node-id），且该目录无 `auth.json` | 起一个真节点，打印它拿到的 env 与该目录内容 |
| I2 | `codex` 命令行里**没有** `--add-dir` | 断言 `_codex_exec_args` 的输出 |
| I3 | 兄弟路径出现在节点产物里 → 记 `cross_node_leak`（advisory），**不**阻断 | 造一条合成泄露跑一遍 |
| I4 | 自己的路径 / 根目标 / 集成目标**不**误报 | 同一批断言 |
| I5 | 未配置 `codex_home` 时行为与今天完全一致 | 现有测试不降（800 例） |
| I6 | 读隔离的现状给出**原始输出**：`--cd node-a` 下读 `node-b/secret.txt` 的结果 | `scripts/verify_isolation_boundary.py --real`（段 1） |
| I7 | 节点命令行里没有 `--add-dir`（读隔离的前提之一） | 断言 `_codex_exec_args` 输出 |
| I8 | 子进程环境**不含**宿主上无关的凭据键，但含系统必需键（PATH 等），且真实 CLI 仍能跑 | `verify_isolation_boundary.py` 段 2/4 + 单测 |

### 4.1 本轮实测（2026-09-22，`codex-cli 0.154.0`）

| 段 | 结果 |
|---|---|
| 1 越权读（`--cd node-a` 读 `node-b/secret.txt`） | **Access is denied** —— 沙箱把读限在 `--cd` 内（翻转 R0-E3 的旧结论，§2.0） |
| 2 凭据面 | 隔离 `CODEX_HOME` 里**没有** `auth.json`；未收窄时子进程环境里有 3 个无关平台凭据（已由 2.4 收窄） |
| 3 越权留痕 | 合成泄露命中兄弟路径；自己的路径不误报 |
| 4 收窄环境可用 | 真实 CLI：退出码 0、回答 `OK`（收窄没有把真实通道弄坏） |

G4 要的是"越权尝试**失败**的原始输出"。本轮拿到的是这个（§2.0 的 `Access is denied`）——
**但它的功劳属于 codex 沙箱，不属于我们的代码**。所以 §4-I6 的定位是"定期重测"：
升级 CLI 之后必须重跑段 1，否则"读隔离还在"就只是一个没人维护的假设。
（本 spec 的第一版把"读隔离做不到"写成了结论，被这一轮实测推翻；旧说法留在 git 历史里，不在这里假装修正过。）

## 5. 未决

| 编号 | 决策 | 现状 |
|---|---|---|
| ISO-1 | 是否引入"每节点独立账号"或容器边界 | **不做**：读隔离已由沙箱提供（§2.0），再加一层账号/容器只会抬高运行成本 |
| ISO-2 | `cross_node_leak` 是否在某些条件下升级为 blocking | 先只做 advisory；要升级需先有"误报率"的实测数据 |
| ISO-3 | 沙箱行为改变的**自动**探测（现在是靠人记得跑段 1） | 先靠发布前清单里的一条手工步骤；要自动就得把段 1 接进 `verify_all.py`（它花 token，需先定"谁付"） |
