## 1. P4-3：重复动作是怎么发生的

管家和看门狗都能发现问题，但**谁也不知道对方已经看到了**：

* 看门狗把僵死节点重新排队，管家同一时刻建议重试 —— 两次重试；
* 管家在等用户确认"要不要取消这棵树"，看门狗看它没进度又休眠一次。

代价不只是白干活：**它会掩盖真实信号**。"这个节点被重试了 3 次"看起来像节点自己
不稳定，其实是两个组件各点了一次 —— 而人会去查节点，不会去查"是不是有人重复动手"。

### 一条规矩

> **谁要处理，谁记账；处理前先查账。**

`claim()` 幂等：同一个 `(kind, target)` 重复认领只刷新时长，不产生第二条。
比"每种动作各写一份去重规则"可靠 —— 去重要随动作种类增长，而账只有一份。

### 四条设计取舍

| 取舍 | 理由 |
|---|---|
| **必须过期**（`expires_at` 必填，上限 24h） | 一条忘释放的认领会让我从此对那个目标闭眼，而看板上一切正常 |
| **只有认领人能释放** | 看门狗不该替管家宣布"管家的介入结束了" |
| 人可以**强制**解除，但必须**留名** | 否则一条卡住的记录会把目标永久锁死 —— 而永久锁死比重复动作更糟 |
| `kind` / `actor` 是**封闭词表** | 自由字符串会让"同一件事"被记成两个 kind，账本形同虚设 |

### 与债务的区别（容易混）

| | 债务（obligation） | 注意账（claim） |
|---|---|---|
| 回答 | 这棵树**还欠什么** | 这件事**谁在处理** |
| 谁看 | 门禁（能不能标完成） | 管家 / 看门狗（要不要动手） |
| 有效期 | 不会自动过期 | **必须过期** |

一张过期的债务是"还没做完"；一张过期的认领是"没人管了，谁都可以接手"。

### 另一向：管家看得到看门狗

这一向**早已存在**（`steward_status._watchdog` 把心跳、守护者结论、机器压力读进
管家的状态快照），所以 P4-3 缺的只是"看门狗尊重管家的标记"那半，
而它由同一张账解决 —— 管家认领 `human_decision`，看门狗查账就跳过。

## 2. P4-2：要解决的不是"能不能调"，而是"调了之后查得到、能改回去"

### 三样缺一不可

1. **谁在什么时候改了什么**（含**旧值**）—— 只看"现在是 5"回答不了"为什么变成 5"；
2. **能回滚** —— 一次调错的并发档会压垮机器，而"改回去"必须一键：否则人会去猜原来的值；
3. **改的理由** —— 审计里最有价值的一列。

### 硬边界不是建议

并发 0 是**静默停摆**，并发 999 是**压垮机器**。两个都不是"用户的自由"。
所以 `coerce()` 按登记表里的 `minimum`/`maximum` 直接拒。

### 危险方向按**方向**判断，不按"值变了"

`machine_safety_min_available_memory_mb` 调**小**才危险（守卫变松），调大是收紧。
把方向搞反会让界面对收紧也弹确认，于是人开始无脑点"确定" —— 那时确认就失效了。

### 一批要么全过、要么全不过

一半生效一半失败是最难查的状态：用户只看到一条错误，而实际改了两项里的第一项。

### 记录先于生效

`apply()` 先写事件、再改配置。反过来会在崩溃时留下一个无人知道的改动 ——
而它看起来和"配置一直都是这样"完全一样。

**复用事件表**而不是新建审计表：`event_records` 已经是"发生了什么"的权威记录，
看板/结论/诊断包都在读它。再开一张表会让同一个改动出现两处，而两处会慢慢不一致。

## 3. 变异测试

| 变异 | 结果 |
|---|---|
| `claim()` 不检查"别人已认领" | ✅ T1 红 |
| `coerce()` 去掉下限校验（并发 0 可过） | ✅ 4 条红 |
| 回滚逐条收集同键（多步回滚产生重复键） | ✅ 端点判据红 —— 这条**抓到的是真 bug** |

第三条值得单独说：多步回滚在同一个档位改过多次时会生成两条 `Change`，
`plan()` 的重复键校验当场拒绝 —— 也就是说**多步回滚曾经完全不可用**，
而界面上的表现只是一句"同一个档位出现了两次"。修法是按 key 收敛、取**最早**那次的旧值。

## 4. 已知限制（如实写下）

* **看门狗侧的接线尚未完成**：`attention.claim()` / `is_claimed_by_other()` 是给
  看门狗用的入口，但看门狗脚本（`scripts/battlefield_watchdog.ps1`）目前**还没有**
  调用它 —— 现在记账的是管家侧与界面。也就是说"防止重复动作"这一层的**机制**已就位、
  判据已就位，但看门狗那一半要等下次改脚本时才真正接上。这是本次交付里最需要说清的一点。
* 认领**不持久化跨重启的语义**：表在库里，但重启后没有任何东西会自动清理过期记录；
  它们只是不再"生效"（`active_claims` 按时间过滤）。长期运行会积累历史行 ——
  清理属于 P5-4（数据保留）。
* 档位调整**重启后才生效**（档位是启动时读入的），界面上明确写了。
  热生效需要重建 `Settings`，那会牵动一堆已持有 settings 的对象，不做。
* 回滚只按"最近 N 次"回退，**不按目标值**回退。想回到某个具体值就直接填那个值。
