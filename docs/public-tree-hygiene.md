# 公开树卫生：内部标识不许出现在会推送到公开仓的文件里

这份文档记的是一次**真实的泄漏事故**（发生在写这份文档的同一轮里）、根因、修法，
以及"以后凭什么不会再犯"。它配的判据是 `api/tests/test_public_tree_hygiene.py`（H1–H4），
扫描器是 `scripts/check_public_tree.py`。

## 1. 事故

内部仓 = 公开仓 + 7 个 overlay 文件（其中 5 个只在内部仓存在）。第一版"整体验收审计"
为了说清双仓状态，在 `docs/acceptance-audit.md` 里把这 7 个文件名**逐个列了出来**，
`scripts/gen_acceptance_audit.py` 里同样列了一份。两个文件都在**公开树**里 ——
于是内部标识被亲手推上了公开仓。

同一轮还清掉一处更隐蔽的：`api/tests/test_diagnostics.py` 验脱敏时用了内部网关的
**真实前缀 + 真实 hex 后缀**当"随便举的例子"，`api/app/diagnostics.py` 的文档表格里
也抄了一份。

发现方式：写 `docs/test-determinism.md` 时顺手跑 `check_public_tree.py --terms-file ...`，
发现本机**连词表文件都没有**；临时建了一份词表，一跑就命中 10 处
（其中 6 处已经在推送出去的提交里）。

## 2. 为什么当时没被抓住（三层，都要记）

1. **词表不在仓库（这是对的），但本机也没有那份词表。** 扫描器不给 `--terms-file`
   时只跑通用规则（本机路径 / 疑似密钥 / 内网地址 / 大文件）—— 也就是"私有标识不进
   公开树"这条规矩**从来没有被自动检查过**。规矩不在判据里，就只是意愿。
2. **扫描器没有进 `verify_all`。** 跑不跑靠人记得，而人不会记得。
3. **审计生成器选择了"把名字列出来"这种写法。** 写的时候想的是"这样最清楚" ——
   这就是这类泄漏最典型的形态：**为了让文档更清楚，把内部名字写进了公开文件**。
   凡是"双仓差异""内部清单""私有配置"这类内容，公开侧只能写**数量与判据位置**。

## 3. 修法

| 位置 | 原来 | 现在 |
|---|---|---|
| `scripts/gen_acceptance_audit.py` | 列出 7 个 overlay 文件名 | 只说"恰好 7 个：5 个只存在于内部仓、2 个是公开树里也有的（被改写了）"，并注明**为什么不列名字** |
| `docs/acceptance-audit.md` | 同上（生成物） | 重新生成；文件名只在运行输出里出现 |
| `api/tests/test_acceptance_audit.py` Q5 | docstring 里带了内部文件名 | 去掉名字，并把审计里那句"5 个 / 2 个"也钉住（只钉总数的话，把"新增"改成"改写"仍然会过，那句话就成了假的） |
| `api/app/diagnostics.py`、`api/tests/test_diagnostics.py` | 内部网关真实前缀 + 真实 hex 后缀 | 中性样张（判据要的是"名字里带 key/token 就脱敏"这个**形状**，不是那个具体名字） |
| `docs/cross-platform.md` | 正则示例写成"盘符 + 用户目录 + 省略号" | 改成 `C:\Users\<用户名>`：既更准确，也不再被通用规则误报 |

## 4. 判据（`api/tests/test_public_tree_hygiene.py`）

| 判据 | 覆盖什么 | 什么时候会红 | 什么时候跳过 |
|---|---|---|---|
| H1 派生式 | 内部仓**新增**的文件名不得出现在工作树里 | 公开树里出现任何一个这类名字（含未提交的改动） | 没有 `internal/main`；或当前 HEAD 是内部分支（那边的文件本来就该出现这些名字） |
| H2 扫描器自测 | 扫描器**能抓到**植入的词 | 扫描器坏了（例如词表规则没接上） | 不跳过 —— 它是"扫描通过"这件事的前提 |
| H3 通用规则 | 本机路径 / 疑似密钥 / 内网地址 / 大文件的命中必须**恰好**是测试里的假样张 | 任何新增命中（含无意写进文档的本机路径） | 不跳过 |
| H4 私有词表 | 用真实词表跑完整扫描，除假样张外 0 命中 | 内部标识进了公开树 | 没配 `CODEX_BATTLEFIELD_PUBLIC_TERMS`（**发布前必须配一次**） |

两条设计说明：

* **H1 扫的是工作树，不是 `origin/main`。** 扫已推送的提交只能在**事后**发现 ——
  而公开出去的东西收不回来。扫工作树则能在 `git add` 之前就红。
* **H1 的名单是现算的**（`git diff --diff-filter=A`），不写死在测试里：写死的话，
  下次换名字就会静默失效。同一理由，内部仓不再新增文件时 H1 会**报错而不是通过**
  （空转的门禁会给出"检查过了"的错觉）。

## 5. 变异记录（怎么知道这些判据能红）

| 变异 | 结果 |
|---|---|
| 在 `docs/_leak_probe.md` 里写入一个内部新增文件名（名字从 git 现取，不手打） | H1 红 |
| 在同一文件里写入一个**新的**假密钥（`sk-ZZZ…`，与样张不同） | H3 红 |
| 把 `check_public_tree.py` 的 `term_rules` 清空 | H2 红（"植入的词没被抓到"） |
| 写入**与样张完全相同**的假密钥 | H3 **不红** —— 这是有意的：命中按"类别 + 字面量"去重，与样张一模一样说明它不是新秘密 |

## 6. 局限与仍未验证

* **H4 依赖本机词表**（环境变量指向仓库之外的文件）。公开克隆里没有词表，这条会跳过；
  内部标识的完整扫描因此**只在配了词表的机器上**发生。
* **词表本身不会自动长大。** 新起一个内部名字时，没人提醒你去加词表 —— 这条缺口
  目前只被 H1 部分覆盖（H1 只管**文件名**，不管出现在正文里的词）。
* H3 的假样张允许清单是**派生**的（"与样张文件里的命中同值即允许"）。它防的是
  "清单自己也被命中导致永远红"，代价是"把样张复制到别处"不会被判红。
* 历史里的泄漏**没有清理**：把文件名清单写进审计的那两个提交仍在公开仓历史里 ——
  工作树修好不等于推出去的字符串消失。清理需要对公开仓做历史重写 + 强推，那是
  **仓库所有者的决定**（`docs/README.md` 的发布说明也写了为什么"历史一旦推出去就很难
  收回"）；本轮只保证工作树与之后的提交干净，并把事实记在这里。
