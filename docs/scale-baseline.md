# 千节点规模基线（P3-6）

判据实现：`api/tests/test_scale.py`（14 例）。
这份文档记录**实测数字与阈值来源**，用来回答"这些阈值凭什么定这么高"。

## 1. 怎么量的

* **真实 SQLite + 真实 ORM**：夹具造 250 / 1000 个节点的树（每层 4 叉，不是单链
  —— 单链树会让"按层聚合"的查询看起来很好而其实没测到宽度），外加 400 条带用量
  的运行记录。**不 mock**：性能问题的来源就是 SQL 与序列化，mock 掉等于没测。
* **预热 2 次 + 取 7 次中位数**。
  ⚠️ 第一版探针只跑一次，得到 `get_tree` 850ms 而 `get_tree(compact_done=False)` 36ms
  —— 后者"更快"只是因为它吃到了前一次留下的 SQLAlchemy mapper 缓存。
  **一次测量量的是缓存预热，不是算法。**
* 单位毫秒，`p50`。

## 2. 干净环境实测（2026-10-16，本机 Windows / Python 3.12）

| 端点 | 250 节点 | 1000 节点 | 规模比 | 荷载（1000 节点） |
|---|---|---|---|---|
| `get_tree`（界面首屏） | 34.2 ms | **129.5 ms** | 3.79 | 640 KB |
| `get_tree(compact_done=False)` | 34.8 ms | 133.2 ms | 3.83 | 640 KB |
| `cost_report` | 4.5 ms | 12.5 ms | 2.76 | 2.4 KB |
| `obligation_index.board` | 2.2 ms | 10.6 ms | 4.92 | 0.3 KB |
| `get_watchdog_state` | 37.0 ms | 119.2 ms | 3.22 | 97 KB |

节点数涨 4 倍时耗时涨 2.8–4.9 倍 —— **亚线性到接近线性**，没有超线性退化。

## 3. 阈值与理由

| 判据 | 阈值 | 基线 | 余量 | 为什么是这个数 |
|---|---|---|---|---|
| S1 首屏 | 700 ms | 130 ms | 5.4× | ROADMAP 要求"首屏 < 2s"，而首屏 = 后端 + 加载 + 渲染；后端留 700ms |
| S2 荷载 | 1 MB | 640 KB | 1.6× | "状态快照不超上下文预算"：超了会在塞 prompt 时**静默截断** |
| S3 `get_tree` | 700 ms | 130 ms | 5.4× | — |
| S3 `cost_report` | 120 ms | 12.5 ms | 9.6× | 它扫整棵子树，给最松的余量 |
| S3 `obligation_board` | 120 ms | 10.6 ms | 11× | 很小，但它是**派生索引**，退化会直接影响看板 |
| S3 `watchdog_state` | 700 ms | 119 ms | 5.9× | — |
| S4 规模比 | < 8.0 | 2.8–4.9 | ~1.6× | 唯一能抓 **O(n²)** 的判据 |

**不要再往上调阈值**：调到抓不住退化就等于没有判据，而"抓不住"的表现恰好是全绿。
要放宽必须先写清"为什么这次退化可以接受"。

## 4. 变异测试（证明阈值真的能红）

| 变异 | 结果 |
|---|---|
| 在 `cost._nodes_of_tree` 里注入 O(n²)（每个节点重扫全表） | ✅ S3 `cost_report` 红（438 ms > 120 ms）、S4 红（比值 12.8 > 8） |
| 同一变异对 `get_tree` 的影响 | ✅ S4 红（比值 17.8–24.3）—— 说明 S4 对**任何**超线性退化都敏感 |

## 5. 已知限制（如实写下）

* **本判据会在 CI/别人机器上 flaky 吗？** 会，所以做了预热 + 中位数 + 4–11 倍余量。
  在 xdist 并行下实测耗时约为干净环境的 4 倍，阈值按那个上界定。连跑 3 次全绿。
* **前端的 2 秒没有被这个文件覆盖**：它量的是后端。真正的"首屏 < 2s"还要算上
  浏览器加载与渲染。P5-3 补上了**真浏览器**（`web/e2e/`），但那一组验的是**接缝**
  （字段、渲染、授权、诊断），**没有量渲染耗时** —— 所以"首屏 < 2s"这句话到这里
  **仍然没有证据**。要量它得在 E2E 里加 `performance.mark` 并对比阈值，
  那是另一件事（而且 CI 机器性能差异会让它变成噪声源）。
* **所以"千节点下界面可交互"这条判据也被拆成了两半**（P3-6 的行里写了）：
  后端侧有实测（130ms/640KB，4–7 倍余量）；前端侧现在的保证是**有界的**
  —— `web/src/virtualization.ts` 把交给布局器的节点数限在
  `DEFAULT_WINDOW_LIMIT`（400）以内，并且**把被挡掉的数量显示出来**
  （`virtualization.test.ts` 13 例 + 变异验证）。有界 ≠ 快：它保证的是
  "不会因为树变大而线性变慢"，不是"多少节点都能 2 秒内画完"。
* 没有量**内存**与**磁盘 I/O**：千节点树的库本身只有 128 KB 量级，还构不成压力。
  要量得等 P5-1（异步化与慢查询基线）一起做。
* `obligation_index.board` 的比值（4.9）最接近上限，样本也最小（2–12 ms 量级，
  计时噪声占比大）。它的绝对预算才是主要判据。
