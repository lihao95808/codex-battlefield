# 千节点规模基线（P3-6）

判据实现：`api/tests/test_scale.py`（14 例）。
这份文档记录**实测数字与阈值来源**，用来回答"这些阈值凭什么定这么高"。

## 1. 怎么量的

* **真实 SQLite + 真实 ORM**：夹具造 250 / 1000 个节点的树（每层 4 叉，不是单链
  —— 单链树会让"按层聚合"的查询看起来很好而其实没测到宽度），外加 400 条带用量
  的运行记录。**不 mock**：性能问题的来源就是 SQL 与序列化，mock 掉等于没测。
* **预热 2 次 + 取 7 次中位数**。
  ⚠️ 第一版探针只跑一次，得到 `get_tree` 850ms 而 `get_tree(compact_done=False)` 36ms
  —— 后者"更快"只是因为它吃到了前一次留下的 SQLAlchemy mapper 缓存。
  **一次测量量的是缓存预热，不是算法。**
* 单位毫秒，`p50`。

## 2. 干净环境实测（2026-10-16，本机 Windows / Python 3.12）

| 端点 | 250 节点 | 1000 节点 | 规模比 | 荷载（1000 节点） |
|---|---|---|---|---|
| `get_tree`（界面首屏） | 34.2 ms | **129.5 ms** | 3.79 | 640 KB |
| `get_tree(compact_done=False)` | 34.8 ms | 133.2 ms | 3.83 | 640 KB |
| `cost_report` | 4.5 ms | 12.5 ms | 2.76 | 2.4 KB |
| `obligation_index.board` | 2.2 ms | 10.6 ms | 4.92 | 0.3 KB |
| `get_watchdog_state` | 37.0 ms | 119.2 ms | 3.22 | 97 KB |

节点数涨 4 倍时耗时涨 2.8–4.9 倍 —— **亚线性到接近线性**，没有超线性退化。

## 3. 阈值与理由

| 判据 | 阈值 | 基线 | 余量 | 为什么是这个数 |
|---|---|---|---|---|
| S1 首屏 | 700 ms | 130 ms | 5.4× | ROADMAP 要求"首屏 < 2s"，而首屏 = 后端 + 加载 + 渲染；后端留 700ms |
| S2 荷载 | 1 MB | 640 KB | 1.6× | "状态快照不超上下文预算"：超了会在塞 prompt 时**静默截断** |
| S3 `get_tree` | 700 ms | 130 ms | 5.4× | — |
| S3 `cost_report` | 120 ms | 12.5 ms | 9.6× | 它扫整棵子树，给最松的余量 |
| S3 `obligation_board` | 120 ms | 10.6 ms | 11× | 很小，但它是**派生索引**，退化会直接影响看板 |
| S3 `watchdog_state` | 700 ms | 119 ms | 5.9× | — |
| S4 规模比 | < 8.0 | 2.8–4.9 | ~1.6× | 唯一能抓 **O(n²)** 的判据 |

**不要再往上调阈值**：调到抓不住退化就等于没有判据，而"抓不住"的表现恰好是全绿。
要放宽必须先写清"为什么这次退化可以接受"。

## 4. 变异测试（证明阈值真的能红）

| 变异 | 结果 |
|---|---|
| 在 `cost._nodes_of_tree` 里注入 O(n²)（每个节点重扫全表） | ✅ S3 `cost_report` 红（438 ms > 120 ms）、S4 红（比值 12.8 > 8） |
| 同一变异对 `get_tree` 的影响 | ✅ S4 红（比值 17.8–24.3）—— 说明 S4 对**任何**超线性退化都敏感 |

## 5. 已知限制（如实写下）

* **本判据会在 CI/别人机器上 flaky 吗？** 会，所以做了预热 + 中位数 + 4–11 倍余量。
  在 xdist 并行下实测耗时约为干净环境的 4 倍，阈值按那个上界定。连跑 3 次全绿。
* **前端的 2 秒现在有数字了 —— 而且没达到。** 上一版这里写的是"仍然没有证据"。
  本轮补了**真浏览器 + 真产物**的判据 `web/e2e/perf-first-screen.spec.ts`：
  用 `web/e2e/seed_scale_tree.py` 造一棵与后端判据**同形**的 1000 节点树（根 + 4 叉 +
  叶子带运行记录），从 `page.goto` 量到 L4 画布上出现第一个节点，走的是 **API 托管的
  `web/dist`**（生产路径，不是 Vite dev server）。本机实测（2026-10-16，Windows）：

  | 次数 | 冷启 | 热启 | 荷载 | 服务端取树（3 次采样） |
  |---|---|---|---|---|
  | 第 1 次 | **4408 ms** | 3757 ms | 580 KB | — |
  | 第 2 次 | **4810 ms** | 3888 ms | 567 KB | 286 / 444 / 1555 ms |
  | 第 3 次 | **3491 ms** | 3424 ms | 567 KB | 358 / 2258 / 1261 ms |
  | 第 4 次（整套 `verify_all` 里） | **2422 ms** | 2203 ms | 567 KB | 1265 / 1208 / 231 ms |

  拆解（第 3 次）：`load=441ms`（页面+bundle，很快）、**两次** `/api/tree`（浏览器侧
  合计 1815 ms）、服务端单次 0.2–2.3 s（抖动极大）。

  **结论：目标 `< 2s` 未达标**（实测 **2.4–4.8 s**，最好的一次 2422 ms 也在目标之上）。判据里因此有两层：
  `TARGET_MS = 2000`（ROADMAP 的目标，**故意留在代码里**，免得从"没做到"漂移成
  "没这回事"）与 `RATCHET_MS = 6000`（**只保证不比现在更慢**，实测 4.8 s 的 1.25 倍余量）。
  **棘轮过了不代表目标达成**，报告与 ROADMAP 都不许这么写。

  下一步的三个线索（都有数字，不用猜）：① 前端**一次首屏取了两次树** —— **已修**
  （`useTreeRefresh` 里 `loadTree()` 写了两遍，且 `loadTree` 的依赖里有 `selectedId`，
  而它每次加载都会被 `setSelectedId` 改一次 → "挂载时拉一次"的 effect 又被触发一次；
  修法是去掉重复调用 + `selectedId` 改走 ref 不进依赖数组。**判据自己证明了修好**：
  拆解里 `tree_requests` 从 2 变成 1，URL 逐字相同的那两个请求只剩一个）。
  ⚠️ 但**首屏墙钟没有因此变快**（修前 2422–4810ms，修后 2985–4289ms，同一量级）——
  所以原来那句"先省一半"的猜测**没有被实测支持**：真正的瓶颈不在这两次请求中的哪一次，
  而在**客户端处理 567KB 荷载**。证据：单独那一次请求，浏览器侧量到 2178ms，
  而同一个 URL 由 Node 侧请求只要 230ms（服务端采样 230/314/235ms）——
  差的那 ~1.9 秒在渲染进程的主线程上（解析 + 派生 + 建节点），不在网络上。
  ② 服务端同一棵树在单元判据里是 130 ms，在**跑着 orchestrator 的实例**上是 0.2–2.3 s
  —— 说明接口本身还好，慢在"与编排循环抢 CPU/库锁"；
  ③ 渲染 1000 个 React Flow 节点本身的成本**已经单独量了**（用浏览器的 long task 观测，
  不改产品代码：`page.addInitScript` 只在判据的页面里注册 `PerformanceObserver`）：
  **主线程长任务 6 次 / 共 786–1025ms / 最长 289–355ms**。

  **④ 最要紧的一条：那 1.5 秒是服务端的"首字节"（TTFB），不是渲染、也不是排队。**
  把 `PerformanceResourceTiming` 拆开记（`start_ms` / `wait_ms` / `body_ms`）之后，
  同一次首屏的数字是：

  | 量 | 值 | 说明 |
  |---|---|---|
  | `cold_ms` | 2771 ms | 到"画布上出现第一个节点" |
  | 树请求 `start_ms` | **436 ms** | 请求**发出**得不晚（排除"前端排了很长的队"） |
  | 树请求 `wait_ms` | **1430 ms** | 从发出到**首字节** —— 服务端在想事情 |
  | 树请求 `body_ms` | 12 ms | 567KB 传完只要 12ms（本机回环） |
  | 主线程长任务 | 786 ms 合计 | 客户端处理（解析 + 派生 + 建节点） |

  也就是说：**瓶颈是服务端对 1000 节点 `/api/tree` 的首字节延迟（0.25–1.5 秒且抖动大）**，
  而单元判据里同一棵树只要 **130 ms**（那里没有编排器在跑）。客户端处理（~0.8 秒）是第二项。
  下一步该量的是**服务端那条路上到底谁在花时间**：`/api/metrics` 已经按路由模板记了 p95，
  在同一个 E2E 里读它（或临时给 handler 打点）就能把"编排循环抢 CPU/库锁"与
  "handler 本身重"分开。**"渲染 1000 个节点很贵"不是主要故事**，
  下一步该动的是 ② 与 ④，而不是再删请求。

  **⑤ 首屏被自己的面板挤住了 —— 已修，首屏 −31%。**
  把首屏那一瞬间的 API 全部记下来（`api_requests`）后看到：页面在 **414–419ms 那一瞬间打了
  15 个请求**，其中两条是重活 —— **`/api/auto-policy` 1343ms、`/api/watchdog/state` 1295ms**，
  而关键路径的 `/api/tree` 是 2366ms。同进程里 Python 的 CPU 密集 handler 被 GIL 串起来，
  所以**两个侧栏面板把树挤到了 2.3 秒**（服务端空闲时同一棵树只要 240ms）。

  修法（`web/src/LeftRail.tsx`）：那两条重活所属的四个面板（Watchdog / CrossProject / Cost / Policy）
  **等树到位再挂**（`view.tree?.tasks.length ? … : null`）；绑定引导 `ProjectOnboarding`
  **不跟着这个门走**（它就是给"还没有树"用的）。面板内容照样出来，只是晚几十毫秒。

  | 量 | 修前 | 修后 |
  |---|---|---|
  | `cold_ms` | 4406 / 4409 ms | **3033 ms**（−31%） |
  | `/api/tree` `wait_ms`（TTFB） | 2299 / 2324 ms | **1167 ms** |
  | `/api/tree` 服务端自报 p50 | 845 / 947 ms | **760 ms** |
  | 两条重活的**开始时刻** | 415 ms（**与树并发**） | 1593 / 1610 ms（**树之后**） |

  仍未达标（3.0s > 2s）。剩下的两个杠杆量得很清楚：**树自己的 TTFB 在负载下 760ms（空闲 240ms）**
  与**客户端渲染 ≈1.0–1.4s**（长任务合计 977ms）。

  **⑥ 那 1 秒其实是"扫进程"，不是树 —— 用 profiler 定住了（本轮最有价值的发现）。**
  现象：`get_tree` 的**第一次**调用 1066–1359ms，之后 133–226ms；连"静置 2.5 秒后"再量的
  第一批也还是 `[1294, 272, 299]` —— 总是"第一次慢"。

  `cProfile` 直接点名（1000 节点，全部 1.359 秒里）：

  | 函数 | tottime | 说明 |
  |---|---|---|
  | `{method 'read' of '_io.TextIOWrapper'}` | **0.895s** | 一次**子进程 stdout** 的读取 |
  | `{built-in method _winapi.CreateProcess}` | 0.031s | 起的那个进程 |
  | `utils._text_quality_score` 等 | ~0.12s | 树自身的文本处理 |

  顺着看代码：`get_tree` 第一步就是 `_sync_live_external_agent_statuses` →
  `_external_codex_processes`，而它是 **PowerShell `Get-CimInstance Win32_Process`** 全表扫描，
  **缓存 TTL 只有 2 秒**。于是：

  * **树本身只要 ~150–250ms**（第 2–4 次调用的数字）；
  * **首屏每次都替一个 2 秒过期的进程扫描付 ~1 秒**（页面静置超过 2 秒后再打开就会命中）；
  * 而且这跟"1000 节点"没有关系 —— 空树一样要付。

  这也解释了为什么"服务端静置采样"仍然是 `[1294, 272, 299]`：**不是负载，是缓存过期**。

  **下一步（下一轮，两个候选，都需要单独的验证）**：
  1. **把这笔开销挪出请求路径**：由后台按 ~1.5 秒刷新那份缓存（请求永远命中热的），
     代价是后台一直在扫进程。**这一轮实现并实测过，但没能证明它有效**：静置后的第一批采样
     仍是 `[1064, 301, 249]`（修前 `[1061, 242, 295]`）—— 也就是说"2 秒缓存过期"这条解释
     **只解释了一部分**，剩下的慢来自别处（服务端自报 p50 733ms、p95 2112ms 仍在抖）。
     按"没换来可测收益的改动不留"的规矩，**已回退**；它作为候选留着，但下次必须先用
     `/api/metrics` 把"哪一段在抖"钉住再动手。
  2. **换掉扫描本身**：`psutil.process_iter(['pid','cmdline'])` 保留"按 CommandLine 过滤"
     的语义，把 0.67–0.9 秒降到几十毫秒。**这一轮试了但没法验证**：本机 `pip install psutil`
     报 `No matching distribution`（这个环境的索引里没有），按"不发布没验过的路径"的规矩
     **没有引入**（psutil 分支与依赖都已回退）。
     `tasklist` 实测 418ms 但**丢掉 CommandLine**，会把无关 codex 进程算成"活跃槽位"，**不能**直接换。

  **这一轮真正落地的只有一条**：把 WMI 全表扫描换成**服务端过滤**
  （`Get-CimInstance -Query "SELECT … WHERE Name='codex.exe'"`）—— cProfile 里那一段从
  **0.895s → 0.672s**（同一棵树本身的成本是 150–250ms）。收益真实但不够，剩下的部分见上面两条。

  **⑦ 结论：那条 ~1 秒路径被拔掉了，首屏本机达标。**
  干净对照（上一轮加了"更久之后"那一批采样，专门用来分开"并发挤慢"与"缓存过期"）：
  服务端**彻底安静**之后第一次 `/api/tree` 仍是 1196ms，紧接着 233/241ms —— 这条把"缓存过期"
  钉死了。于是落地两条：

  * **启动时先热一次**（`lifespan` 里 `await asyncio.to_thread(...)`）；
  * **后台每 1.5 秒刷新那份缓存**（`_external_process_scan_loop`，interval < TTL 2 秒）。

  实测（两连跑，判据 `web/e2e/perf-first-screen.spec.ts`）：

  | 量 | 修前 | 修后 |
  |---|---|---|
  | 页面取树 TTFB（`wait_ms`） | 1032–1165 ms | **253–277 ms** |
  | `cold_ms` | 2422–4810 ms | **1601 / 1891 ms**（**达标**，目标 2000ms） |
  | 服务端自报 `/api/tree` p50 | 675–787 ms | **272–283 ms** |
  | 主线程长任务 | 915–1025 ms | 860–974 ms（**下一个大头**） |

  判据里因此多了一条**回归钉子**：页面取树 TTFB `< 700ms`（离修好的 250ms 有 2.7 倍余量、
  离坏掉的 >1000ms 有清晰间隔）—— 谁把后台刷新删掉，这条会红，而不是悄悄变慢。

  **仍未验**：慢机器/CI 上的首屏（判据在 `process.env.CI` 下跳过）。下一步的最大项是
  **客户端渲染（长任务 ~0.9s）**：DOM 只有 400 节点（虚拟化生效），所以它主要是
  JSON 解析 + 派生 + elkjs 对 400 个节点的布局。
  `psutil` 那条候选仍然留着（本机索引里没有，装不上 → 无法验证）：它能把剩下那 0.67 秒
  也拿掉，让"后台刷新"这件事彻底不再需要。
  **CI 上量不出来（已如实记下）**：`run 38965425892`（windows-latest）跑到这条时**整套用例超时**
  ——`apiRequestContext.get: Test timeout of 180000ms exceeded`，E2E 步 `1 failed / 6 passed`。
  也就是说在这台 2 vCPU 的 CI runner 上，千节点首屏**走不完 180 秒**。所以判据在 `process.env.CI`
  下**跳过并写明原因**（不是静默跳过）：CI 上量到的是 runner 的容量，不是"首屏"。
  这条数字本身有意义：**慢机器上离 2s 差得更远**（本机最快 2422ms 也在目标之上）。
  这也让"首屏慢在哪"更值得查 —— 见下面 ①②③。
* **所以"千节点下界面可交互"这条判据仍然是两半**（P3-6 的行里写了）：
  后端侧达标（130ms/640KB，4–7 倍余量）；前端侧现在有了**实测数字与棘轮**，
  但**目标未达标**。`web/src/virtualization.ts` 把交给布局器的节点数限在
  `DEFAULT_WINDOW_LIMIT`（400）以内并且把被挡掉的数量显示出来（`virtualization.test.ts`
  13 例 + 变异验证）—— 有界 ≠ 快：它保证的是"不会因为树变大而线性变慢"。
* 没有量**内存**与**磁盘 I/O**：千节点树的库本身只有 128 KB 量级，还构不成压力。
  要量得等 P5-1（异步化与慢查询基线）一起做。
* `obligation_index.board` 的比值（4.9）最接近上限，样本也最小（2–12 ms 量级，
  计时噪声占比大）。它的绝对预算才是主要判据。
